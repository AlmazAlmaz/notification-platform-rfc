# Notification Platform — архитектурное проектирование

Домашняя работа №4: требования к централизованной платформе уведомлений онлайн-банка и RFC о гарантированной доставке критичных сообщений с автоматическим failover push → SMS → email.

**Основной документ: [RFC](docs/02-rfc.md).** Он оформлен по структуре шаблона задания. Рекомендуемый вариант — Kafka + PostgreSQL + собственный автомат доставки; альтернативный — Temporal durable workflows.

## Основные расчётные ориентиры

- 10 млн MAU, 3 млн DAU, 300 тыс. concurrent users.
- 30 млн кандидатов уведомлений в сутки, из них 6 млн критичных; 5 маркетинговых кандидатов проходят фильтр согласий и частоты.
- Целевой пик 8 000 logical/s; 2 000 critical/s. Кампания на 1 млн получателей за 10 минут входит в маркетинговую квоту.
- Проектные цели: p99 первой передачи провайдеру ≤1 с; ≥99,9% eligible critical с подтверждением допустимого уровня ≤60 с.
- Резерв N−1 и два независимых SMS-провайдера по 2 200 запросов/с рассматриваются как условия для нагрузочной проверки и договора.

**Границы гарантии:** сохранность принятого сообщения и контролируемое восстановление — обязательный внутренний контракт. Получение человеком при недоступности всех каналов безусловно гарантировать нельзя. Принятие провайдером, получение конечной точкой и прочтение различаются; физический дубль между каналами после неизвестного исхода полностью исключить невозможно.

## Проверка и воспроизведение

Достаточно Python 3.10+:

```bash
python scripts/capacity.py
python scripts/verify.py
```

На Windows вместо `python` можно использовать `py`. Для чтения работы программы запускать не требуется: диаграммы уже сохранены в SVG и PNG. Их пересборка описана в [инструкции](diagrams/README.md).

Это архитектурное предложение, а не реализованный сервис. Расчётные квоты, количество узлов, сроки, цены и производительность явно обозначены как допущения. Production load/chaos/security tests не проводились; их профиль и критерии допуска описаны в RFC. Итоговую оценку выставляет преподаватель.
